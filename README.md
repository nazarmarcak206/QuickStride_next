# QuickStride CRM — Telegram Mini App на Next.js

CRM для українських фрилансерів: клієнти, проєкти, оплати, справи.
Дані живуть у Supabase, вхід — через Telegram (Mini App), у браузері без
Telegram працює демо-режим на localStorage (`quickstride.crm.v1`).

## Запуск

```bash
pnpm install
pnpm dev        # http://localhost:3000
pnpm build && pnpm start   # продакшн-білд
pnpm check      # строгий typecheck
pnpm test       # vitest: гроші, автентифікація, ізоляція даних
```

### Налаштування сервера

1. Створіть `.env` з `.env.example` і заповніть: `TELEGRAM_BOT_TOKEN`,
   `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SESSION_SECRET` (≥32 символи).
   Секрети живуть лише в змінних середовища — ні в репозиторії, ні в звітах.
2. Виконайте `supabase/probe_schema.sql` у SQL Editor: він лише читає фактичну
   схему й порівнює її з очікуваннями коду. Підтверджені відповідності:

   | модель застосунку | колонка в базі | тип у базі |
   | --- | --- | --- |
   | `Payment.date` | `crm_payments.paid_on` | date NOT NULL |
   | `Payment.type` | `crm_payments.payment_type` | text NOT NULL |
   | `Reminder.datetime` | `crm_reminders.due_at` + `crm_reminders.timezone` | timestamptz NOT NULL + text NULL |
   | `Project.deadline` | `crm_projects.deadline` | date NULL |
   | власник запису | `owner_id` (uuid → `crm_users.id`) | uuid |

   Міждомейну цілісність у базі тримають **складені** зовнішні ключі, які вже
   існують (`(owner_id, client_id)`, `(owner_id, project_id, currency)`,
   `(owner_id, project_id)`). Міграція шукає покриття за набором колонок і НЕ
   додає однакових одинарних FK: вони не скасовували б наявних правил
   `ON DELETE`, а лише плутали б щодо того, що станеться при видаленні.
   Єдине нове відношення — `owner_id → crm_users` (його складені ключі не
   покривають). `owner_id NOT NULL` застосовується лише там, де жоден наявний
   FK не робить `SET NULL` у цю колонку — інакше «відвʼязати від клієнта»
   раптом стало б помилкою; міграція повідомляє про кожен такий випадок.

   Переклад — єдиний у `lib/server/columns.ts`; інтерфейс і бізнес-логіка
   далі працюють із звичними іменами.
3. Застосуйте `supabase/migrate_crm.sql`. Файл адитивний: нічого не видаляє і
   не перестворює. Розрахований на **порожні** `crm_*` (перевірено: 0 записів),
   тому обмеження створюються повністю валідованими, а не `NOT VALID`. Якщо в
   таблицях уже є рядки без обмеження власника — міграція зупиняється без
   жодних змін. Повторний запуск — безпечний no-op.
4. Перевірте результат: `supabase/verify_after_migration.sql` (лише читання;
   smoke-тест функції виконується в транзакції з `ROLLBACK`, тож тестових
   рядків не залишається). Після перевірки в Telegram —
   `supabase/cleanup_test_data.sql` (спершу перегляд, видалення розкоментовується
   свідомо і лише за id тестових акаунтів).
4. У BotFather увімкніть Menu Button / Web App на адресу розгортання.

Без заповненого `.env` маршрути відповідають 503 — застосунок поза Telegram
продовжує працювати в демо-режимі, у Telegram показує екран помилки з повтором.

### Локальний режим розробки без Telegram

Типово браузер без Telegram працює лише на локальних даних (демо-режим) і до
сервера не ходить. Якщо потрібне справжнє CRUD у базі з браузера — у власному
`.env.local`:

```bash
DEV_LOGIN=true
DEV_TELEGRAM_USER_ID=<ваш числовий Telegram id>   # дізнати: @userinfobot
NEXT_PUBLIC_DEV_LOGIN=true
pnpm dev
```

`POST /api/auth/dev` працює лише за `NODE_ENV=development` і `DEV_LOGIN=true`;
у продакшн-білді маршрут завжди відповідає 404. Особа береться виключно з
серверного середовища, запит не передає нічого — обрати чужий акаунт чи
обійти авторизацію неможливо.

## Як це працює

- **Автентифікація.** Клієнт надсилає сирі `initData` на `POST /api/auth/telegram`.
  Сервер сам перевіряє HMAC-підпис токеном бота і свіжість `auth_date`
  (24 год за замовчуванням) — `initDataUnsafe` і передані з клієнта id не
  довіряються. Успіх → знаходиться або створюється акаунт і ставиться
  HttpOnly-cookie `qs_session` (підписаний HMAC токен, 30 днів).
- **Ізоляція даних.** Кожен запит даних проходить через сесію; кожен запит до
  Supabase фільтрується за `owner_id`, а власника проставляє сервер (lib/server/repo.ts).
  Клієнти, проєкти, оплати, справи й налаштування — тільки свої. Звʼязки
  (проєкт → клієнт, оплата → проєкт) перевіряються і на сервері, і на рівні бази.
- **Прямого доступу до бази немає.** RLS увімкнено без політик на всіх шести
  таблицях, права `anon`/`authenticated` зняті, виконання RPC дозволене лише
  серверу. `service_role` отримує права явно (не «через PUBLIC»), бо саме він
  — єдиний шлях у базу після перевірки Telegram initData.
- **Валюти та повторні оплати.** Правила з lib/payments.ts застосовуються і на
  сервері: оплата лише у валюті проєкту (409), ідентифікатор запису — uuid,
  який генерує клієнт, тож повторний запит не створює другу оплату
  (`duplicate: true`). Проєкт із передоплатою зберігається однією транзакцією
  в базі (RPC-функція) — або обидва записи, або жоден.
- **Часовий пояс справ.** `due_at` у базі — абсолютний момент (timestamptz),
  тому місцевий час перетворюється через пояс, а не обрізається рядок
  (`lib/timezone.ts`): запис — `wall-clock + пояс власника → момент`,
  читання — `момент + пояс рядка → wall-clock`. Вжитий пояс зберігається в
  `crm_reminders.timezone`, тож зміна поясу в налаштуваннях не «зсуває»
  уже створені справи. Дати, яких не буває (весняний стрибок), зсуваються на
  перший реальний момент; подвійні (осінній перехід) — беруть першу подію.
- **Дати.** `paid_on` і `due_at` у базі NOT NULL, і продукт теж не залишає
  вибору: справа без дати не має де стояти в «найближчих дедлайнах», а оплата
  без дати псує звіт за місяцем — тому порожня дата відхиляється на сервері
  зрозумілим 400. `deadline` навпаки є необовʼязковим: порожнє значення моделі
  зберігається як NULL (пустий рядок для `date` некоректний) і читається назад
  як «дедлайн не задано».
- **Демодані.** Автоматичного перенесення немає. На сторінці налаштувань
  акаунта є явне «Перенести локальні дані» з підтвердженням; імпорт
  детермінований (id — UUIDv5 з пари `owner_id` + локальний id), безпечний
  при повторі. Локальні дані ніколи не видаляються автоматично — це окрема
  свідома дія.

## Структура

- `app/` — сторінки `/`, `/projects`, `/finance`, `/clients`, `/reminders`,
  `/settings`; `app/api/` — серверні маршрути (auth, state, clients, projects,
  payments, reminders, settings, import/demo)
- `components/` — навігація, форми, шітки, тема
- `lib/` — типи, гроші (копійки), ідентифікатори (`lib/ids.ts` — uuid),
  store (demo/server), серверні модулі `lib/server/` (telegramAuth, session,
  supabaseRest, repo, validate, importDemo, users, devLogin, **columns** —
  відповідність імен моделі фактичним колонкам бази)
- `supabase/probe_schema.sql` — звірка фактичної схеми, поточних обмежень,
  застосованих міграцій і побічних таблиць (лише читання)
- `supabase/migrate_crm.sql` — єдина адитивна міграція під `crm_*`:
  `crm_settings`, індекси `owner_id`, валідовані FK/NOT NULL/CHECK, RLS без
  політик, явні гранти `service_role`, RPC-функція
  `qs_create_project_with_prepayment` (атомарний запис проєкту з передоплатою)
- `supabase/verify_after_migration.sql` — перевірка структури, прав, функції й
  цілісності власників; smoke-тест у транзакції з відкатом
- `supabase/cleanup_test_data.sql` — прибирання записів тестових акаунтів
  (перегляд → свідоме розкоментування видалення)
- `supabase/schema.sql` — застарілий скрипт, навмисно без виконуваного SQL

## Перевірка перед розгортанням

- два різні Telegram-акаунти бачать тільки свої дані й не можуть змінити
  чужий запис за прямим uuid;
- підроблений або прострочений `initData` відхиляється (401);
- стан синхронізується між пристроями одного акаунта;
- без мережі в Telegram — екран помилки з повтором, демо-режим не вмикається мовчки;
- `POST /api/auth/dev` у продакшн-білді відповідає 404.
